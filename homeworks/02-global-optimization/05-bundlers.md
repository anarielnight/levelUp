# Оптимизация загрузки скриптов
### Базовый уровень: Управление парсингом HTML (async vs defer)
По умолчанию скрипты блокируют парсинг HTML. Мы управляем этим с помощью атрибутов тега `<script>`:
* **Обычный** `<script>`: Блокирует HTML-парсинг. Браузер скачивает и сразу выполняет его. Используется только для критически важного кода (например, инициализация аналитики или темы до рендеринга страницы).
* **defer**: Скрипт скачивается в фоновом режиме и выполняется строго после полной сборки DOM, но до события DOMContentLoaded. Порядок выполнения скриптов гарантирован (как в HTML). Это стандарт для основного бандла приложения.
* **async**: Скрипт скачивается в фоне и выполняется сразу, как только скачался, прерывая парсинг HTML. Порядок выполнения не гарантирован. Идеально для независимых сторонних скриптов (метрики, чаты, реклама).

### Уровень архитектуры бандла: Разделение кода (Code Splitting)

Мы не должны отдавать пользователю один монолитный JS-файл на 2 МБ. Внедряют следующие подходы:
* **Route-based Splitting**: Ленивая загрузка страниц. С помощью `React.lazy` / `dynamic imports (Next.js)` код страницы скачивается только тогда, когда пользователь на неё переходит.
* **Component-based** / **Interaction Splitting**: Загрузка тяжелых компонентов (например, графиков или редакторов текста) только по триггеру — наведению мыши, фокусу или клику (Pattern: Import on Interaction).
* **SplitChunksPlugin (Webpack/Vite)**: Вынесение node_modules (React, Lodash и т.д.) в отдельный vendor.js чанк. У этих библиотек высокий TTL (время жизни) кэша, они редко меняются, поэтому их нужно кэшировать отдельно от бизнес-логики.

### Приоритезация ресурсов (Resource Hints)

Браузер должен знать о важных скриптах заранее:
* `preload (<link rel="preload" as="script">)`: Указывает браузеру скачать скрипт с максимальным приоритетом прямо сейчас, так как он понадобится на текущей странице (например, чанк для критического интерактивного элемента).
* `prefetch (<link rel="prefetch">)`: Скачивание скрипта с низким приоритетом в моменты простоя браузера, потому что он понадобится на следующих страницах.


## Бандлеры
* **Классические бандлеры (Webpack, Rollup)**: Работают на основе построения полного графа зависимостей (Dependency Graph) в памяти, трансформации кода (Babel) и последующей сборки в файлы. В проде Webpack до сих пор лидирует благодаря мощной экосистеме плагинов и гибкому разделению кода.
* **Современные инструменты (Vite, ESBuild, Rspack)**:
	* В development-режиме Vite полностью отказывается от бандлинга, отдавая файлы как Native ES Modules (ESM). Браузер сам запрашивает нужные импорты, а компиляция «на лету» (On-demand) делегирована сверхбыстрому esbuild (написанному на Go).
	* В production-режиме Vite использует Rollup, так как отдача сотен мелких ESM-файлов в прод неэффективна из-за сетевых задержек (даже с HTTP/2+).
	* Rspack / Turbopack: Написанные на Rust альтернативы Webpack, которые сохраняют его гибкость конфигурации, но ускоряют сборку в десятки раз.


## Bundler Analyzer
Webpack Bundle Analyzer (или аналогичный плагин для Vite) — это рентгеновский снимок твоего приложения.
Когда ты просто собираешь проект, ты видишь на выходе безликие файлы, например: main.a8f9c.js размером 2 МБ. Это огромный «черный ящик». Браузер пользователя будет долго его скачивать и спотыкаться при обработке.
Плагин превращает этот файл в интерактивную карту из цветных кирпичиков.
* Размер кирпичика равен физическому весу кода. Чем больше библиотека или компонент весит, тем больше её квадрат на карте.
* Вся карта кликабельна: можно «провалиться» внутрь любого чанка и увидеть, из каких папок и файлов он состоит.

Способы применения:
* визуальное отслеживание самых тяжеловесных библиотек по размеру занимаемого на карте места для дальнейшего возможного рефакторинга их использования и подлючения
* отслеживание одинаковых библиотек с разными версиями, которые тянут внешние библиотеки
* отслеживание разделения кода по ролям/страницам

## Chunk
Чанкование — это баланс между эффективностью кэширования и скоростью загрузки. Настраивается через optimization.splitChunks в Webpack или output.manualChunks в Vite/Rollup

* **Vendor Chunking**: Вынесение стабильных библиотек (react, lodash) в отдельный чанк. Поскольку их код меняется редко, браузер кэширует их «намертво», а пользователи скачивают только чанки с бизнес-логикой при новых релизах.
* **Dynamic Chunks (Async)**: Создаются автоматически при использовании динамических импортов import(). Код загружается только по требованию (смена роута, клик по кнопке).
* **Shared Chunks**: Вынесение общих компонентов или утилит, которые используются в нескольких независимых точках входа, в отдельные файлы, чтобы избежать дублирования кода.

Слишком много мелких чанков — это плохо из-за накладных расходов на сетевые запросы и парсинг. Слишком мало — плохо для кэша.

Паттерны загрузки чанков:

* **Загрузка по требованию (On Demand / Смена роута)**: Пользователь сидит на Главной странице. Он нажимает кнопку «Перейти в Корзину». В этот момент браузер делает быстрый сетевой запрос, докачивает чанк корзины (basket.chunk.js) и мгновенно отрисовывает её.
* **Загрузка по взаимодействию (On Interaction)**: У тебя на странице есть кнопка «Открыть онлайн-чат поддержки». Сам чат весит очень много. Мы настраиваем код так: как только пользователь наводит мышку на кнопку чата, браузер понимает, что сейчас начнется взаимодействие, и в фоновом режиме за доли секунды скачивает чанк чата. Клик — и чат уже открыт без задержек.
* **Предзагрузка (Prefetch)**: Если пользователь находится на Главной странице, а у нас в фоне есть свободный интернет-трафик, мы можем тихонько сказать браузеру: «Пока пользователь читает текст, скачай-ка с самым низким приоритетом чанк Личного кабинета. Скорее всего, он пойдет туда дальше». Когда пользователь нажмет кнопку, чанк уже будет лежать в кэше компьютера.

## Treeshaking, Native Module
Tree Shaking (в переводе «тряска дерева») — это процесс удаления «мертвого» (неиспользуемого) кода из финального бандла.

Tree Shaking возможен только благодаря Native ES Modules (ESM) — то есть синтаксису import и export.
До ESM в мире JavaScript правил формат CommonJS (require / module.exports). С ним «тряска» не работает. Давай сравним почему:
* **CommonJS (Динамический)**: Код можно импортировать внутри условия if или высчитать путь к файлу на лету: require('./modules/' + variable). Сборщик, когда читает такой код, понятия не имеет, выполнится это условие или нет. Ему приходится включать в бандл вообще весь код на всякий случай.
* **ESM (Статический):** Импорты и экспорты всегда находятся на самом верху файла. Ты не можешь засунуть import внутрь функции или условия if (для этого есть динамический import(), но это другая история). Сборщик может прочитать код, не запуская его, построить строгую карту зависимостей и сразу увидеть: "Ага, функция calculateTax экспортируется, но ни в одном файле проекта она не импортируется. Вычеркиваем!"


Главный враг Tree Shaking: Side Effects (Побочные эффекты)

Самая частая проблема на реальных проектах: ты вроде бы написал ESM-код, но бандл все равно огромный, и Tree Shaking не работает. Почему? Сборщик боится проводить оптимизацию, если подозревает Side Effects.

Побочный эффект — это когда код при своем импорте делает что-то во «внешнем мире», помимо простого экспорта функций.

```
// Файл утилит utils.js
export const add = (a, b) => a + b;

// ПОБОЧНЫЙ ЭФФЕКТ: код меняет глобальный объект window!
window.isMyAppLoaded = true; 
```
Если ты импортируешь только функцию add, сборщик захочет удалить остальной код. Но он видит строчку с window и думает: "Если я вырежу этот файл, глобальный флаг isMyAppLoaded не создастся, и приложение сломается. Безопаснее оставить этот файл целиком". В итоге Tree Shaking блокируется.

Как это решить? Мы явно говорим сборщику, что наш проект (или конкретная библиотека) «чистая». Для этого в файле package.json пишется свойство:
```
{
  "name": "my-app",
  "version": "1.0.0",
  "sideEffects": false
}
```
Флаг `"sideEffects": false` — это смелое заявление для сборщика: "Чувак, тут нет никаких скрытых модификаций `window` или глобальных стилей. Если видишь, что функция не используется — вырезай её без пощады".

Если в проекте все же есть файлы с эффектами (например, глобальные CSS-файлы), их можно добавить в исключения:
```
"sideEffects": [
  "*.css",
  "./src/polyfills.js"
]
```

### Пример из жизни: как разработчики ломают Tree Shaking
Очень популярная ошибка — экспорт дефолтного объекта.
```
// math.js
const min = (a, b) => a < b ? a : b;
const max = (a, b) => a > b ? a : b;

export default { min, max }; // Экспортируем ОДИН большой объект


// main.js
import math from './math.js';
console.log(math.min(1, 2)); 
```
Поскольку ты импортировал целый объект math, сборщик не сможет вырезать функцию max. Он не умеет частично разрушать объекты в рантайме.
Как надо:
```
// math.js
export const min = (a, b) => a < b ? a : b;
export const max = (a, b) => a > b ? a : b; // Именованные экспорты

// main.js
import { min } from './math.js'; // Импортируем строго то, что нужно
console.log(min(1, 2)); // Функция max будет полностью удалена из бандла!
```
