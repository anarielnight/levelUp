# Оптимизация загрузки head
Главное правило оптимизации head: скачать и выполнить критическое как можно раньше, а некритическое — отложить, чтобы не блокировать поток.

### Правильный порядок элементов (Порядок решает всё)

Браузер читает ```<head>``` строго сверху вниз. Ошибка в порядке тегов может заблокировать параллельную загрузку ресурсов.

Идеальная структура ```<head>```:
```
<head>
  <!-- 1. Мета-данные и кодировка (должны быть в первых 1024 байтах) -->
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>Заголовок страницы</title>

  <!-- 2. Подключения к сторонним серверам (Early Connections) -->
  <link rel="preconnect" href="https://example.com">
  <link rel="dns-prefetch" href="https://example.com">

  <!-- 3. Прелоад критических ресурсов (Высокий приоритет) -->
  <link rel="preload" href="/fonts/inter.woff2" as font type="font/woff2" crossorigin>
  <link rel="preload" href="/images/hero-banner.webp" as="image" fetchpriority="high">

  <!-- 4. Критический CSS (inline) или основной CSS -->
  <style>/* Critical CSS: стили для первого экрана */</style>
  <link rel="stylesheet" href="/styles/main.css">

  <!-- 5. Отложенные скрипты -->
  <script defer src="/js/app.js"></script>
  <script async src="https://google-analytics.com"></script>
</head>
```

Почему именно такой порядок?
* meta charset в самом верху: Если браузер наткнется на него слишком поздно, ему придется перепарсить HTML заново с новой кодировкой.
* preconnect перед CSS: Браузер начнет устанавливать соединение с API/CDN параллельно с тем, как качает стили.
* CSS перед скриптами: Браузер не будет выполнять JS-скрипты, пока не построится CSSOM (потому что JS может запрашивать стили через getComputedStyle). Поэтому CSS должен загружаться максимально быстро.

### Борьба с блокировкой рендеринга (Render-Blocking)
По умолчанию и ```<link rel="stylesheet">```, и ```<script>``` блокируют рендеринг страницы. Пока они не скачаются, пользователь видит белый экран.

Как оптимизировать CSS:
1. Critical CSS (Критический CSS): Вырезаем стили, необходимые только для отрисовки первого экрана (инструментами вроде Critical или Penthouse), и вставляем их инлайново в тег ```<style>``` прямо в `head`.
2. Асинхронная загрузка остального CSS: Основной тяжелый файл стилей загружаем так, чтобы он не блокировал страницу:
```
<link rel="preload" href="heavy-styles.css" as="style" onload="this.onload=null;this.rel='stylesheet'">
<noscript><link rel="stylesheet" href="heavy-styles.css"></noscript>
```

Как оптимизировать JS:

Никогда не используйте обычные `<script src="...">` в head. Они останавливают парсинг HTML. Наш выбор — defer или async.

### Предварительное подключение (Resource Hints)
Если страница запрашивает данные с других доменов (шрифты Google, аналитика, CDN со скриптами), браузер тратит драгоценное время на DNS-резолв, TCP-транзакцию и TLS-согласование. Мы можем ускорить это:
* `preconnect` — делает все три шага (DNS + TCP + TLS) заранее. Отлично подходит для критических доменов (например, вашего API).
```
<link rel="preconnect" href="https://my-backend.com">
```
* `dns-prefetch` — делает только DNS-lookup. Используется как фолбек для старых браузеров или для некритичных сторонних доменов (трекеров, рекламы), чтобы не держать открытыми лишние TCP-соединения.

### Нюансы
* Не злоупотребляйте `preload`. Если закинуть туда 20 ресурсов, они забьют всю сеть, и загрузка действительно критических файлов (бандла) затормозится, что ухудшит метрику TBT (Total Blocking Time).
* Всегда ставьте `crossorigin` для прелоада шрифтов. Даже если они лежат на вашем домене. Без этого атрибута браузер скачает шрифт дважды.
* Разделяйте адаптивные изображения. Если у вас на первом экране баннер, используйте медиа-выражения прямо в прелоаде:
```
<link rel="preload" href="bg-mobile.webp" as="image" media="(max-width: 599px)">
<link rel="preload" href="bg-desktop.webp" as="image" media="(min-width: 600px)">
```
## Defer/Async/Module
Главная проблема обычного тега `<script>` в том, что он блокирует парсинг HTML. Браузер останавливается, скачивает скрипт, выполняет его, и только потом идет дальше. Чтобы этого избежать, мы управляем фазами загрузки (fetching) и выполнения (execution).
| Атрибут | Загрузка (Fetching) | Выполнение (Execution) | Порядок выполнения |
| --- | --- | --- | ---|
| Обычный `<script>` | Блокирует HTML | Сразу после загрузки (блокирует HTML) | Строго по порядку в DOM |
| async | Асинхронно (параллельно с HTML) | Сразу после загрузки (блокирует HTML) | Кто первый скачался, тот и выполнился|
| defer | Асинхронно (параллельно с HTML) | После полной сборки DOM (перед DOMContentLoaded) | Строго по порядку в DOM |
| type="module"| Асинхронно (по умолчанию как defer) | После полной сборки DOM | Строго по порядку в DOM |

Когда что применять на практике:
* `defer` — наш выбор по умолчанию для основного бандла приложения (SPA, UI-логика). Скрипт качается не блокируя страницу, выполняется когда DOM готов, и мы уверены в порядке зависимостей.
* `async` — идеально для независимых сторонних скриптов (аналитика типа Google Analytics, Яндекс.Метрика, пиксели соцсетей, чаты поддержки). Им не нужен весь DOM, и не важно, какой скрипт выполнится первым.
* `type="module"` — современные ES-модули по умолчанию ведут себя как defer. Но если добавить к ним async `(<script type="module" async>)`, то они превратятся в async модули, выполняясь сразу после загрузки.

## Подсказки браузеру: preload vs prefetch
Это механизмы rel для тега `<link>,` которые помогают приоритизировать ресурсы. Их часто путают, но у них принципиально разные задачи.

* `preload` — это директива высокого приоритета для текущей страницы. Мы говорим браузеру: «Ты еще не знаешь об этом ресурсе (например, он запрятан внутри CSS), но он мне точно понадобится прямо сейчас. Качай немедленно».
  * Кейсы: Шрифты (Critical Fonts), важные изображения на первом экране (LCP-картинки), критический CSS.
  * Важно: Для шрифтов обязательно указывать crossorigin, иначе они скачаются дважды.
* `prefetch` — это подсказка низкого приоритета для следующих страниц/шагов пользователя. Браузер скачает ресурс только тогда, когда освободится и будет простаивать (в фоне).
  * Кейсы: Сплитованные чанки для других страниц. Например, пользователь сидит на главной, а мы в фоне скачиваем код для страницы «Личный кабинет», куда он, скорее всего, кликнет.
