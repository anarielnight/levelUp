# Оптимизация загрузки ресурсов

## Картинки
* Современные форматы и фолбеки: На production мы полностью автоматизируем конвертацию картинок. Для фото используем AVIF (максимальное сжатие) и WebP как основной стандарт, оставляя старый добрый JPEG/PNG только в качестве фолбека через элемент ```<picture>```:
```
<picture>
  <source srcset="image.avif" type="image/avif">
  <source srcset="image.webp" type="image/webp">
  <img src="image.jpg" alt="Описание" loading="lazy" width="800" height="600">
</picture>
```
* Адаптивность (Responsive Images): Отдавать картинку 3000px на экран смартфона — преступление. Используем srcset и sizes для генерации пула картинок под разные device-pixel-ratio (1x, 2x, 3x) и брейкпоинты. На проектах обычно настраиваем автоматический пайплайн (например, через sharp в Node.js, плагины для Vite/Webpack или cloud-сервисы вроде Cloudinary/Imgix).

* Борьба с Layout Shift (CLS): Всегда жестко прописываем атрибуты width и height для <img>. Браузер до загрузки файла резервирует под него aspect ratio, что предотвращает прыжки контента.

* Lazy Loading: Для всего, что находится ниже первого экрана (below the fold), включаем нативный loading="lazy". Для более сложного контроля (например, плавной загрузки с эффектом blur/placeholder) пишем кастомные хуки на базе IntersectionObserver.

## SVG
С SVG нужен тонкий баланс, так как это код, нагружающий CPU парсингом DOM.

* Очистка и минификация: Дизайнеры экспортируют из Figma кучу мусора (metadata, editor-data, скрытые слои, громоздкие пути). Все SVG прогоняются через SVGO (встроенный в Webpack/Vite сборщик).

* Выбор метода встраивания:
  * Inline SVG ```(<svg>... </svg>)```: Используем только для критических иконок и элементов, где нужен динамический JS/CSS (изменение fill по ховеру, анимации). Минус: раздувает HTML-документ и не кэшируется отдельно.
  * SVG-спрайты ```(<use href="sprite.svg#icon"/>)```: Отличный способ для иконочных шрифтов. Спрайт загружается один раз и кэшируется.
  * Тег ```<img>``` или ```background-image```: Для независимых SVG-иллюстраций, которые не требуют кастомизации стилей. Кэшируются браузером идеально.

* Вектор vs Растр: Если в SVG зашит base64 растровый кусок или внутри тысячи сложных кривых (например, детализированная карта), SVG начинает тормозить при рендере. В таких случаях принимают архитектурное решение перевести это в WebP/AVIF или Canvas.

## Стратегии доставки и приоритеты (Network Level)
* Разделение на "Above the fold" и "Below the fold":
  * Картинки, которые формируют LCP (Largest Contentful Paint) на первом экране (например, баннер), мы никогда не грузим лениво.
  * Более того, мы явно повышаем им приоритет через ```<link rel="preload" as="image">``` или атрибут ```fetchpriority="high"```:
```
<img src="hero.webp" fetchpriority="high" alt="Hero">
```

* Кэширование и CDN: Настройка правильных заголовков Cache-Control: public, max-age=31536000, immutable для статики. Раздача тяжелого медиаконтента строго через CDN (ближе к пользователю — меньше latency).

* Client Hints: Если инфраструктура позволяет, настраиваем HTTP Client Hints (Sec-CH-Viewport-Width, DPR), чтобы сервер сам отдавал нужный размер картинки на лету на основе заголовков запроса браузера.
