## Objects
### Hidden classes
Движок V8 использует под капотом скрытые классы, типизируя объекты. Для того. чтобы это работало оптимально, нужно задавать свойства в одном и том же порядке. 
Каждое собавление или удаление свойства в объект создает новый или переиспользует аналогичный (включая порядок свойств) класс

```
// Порождает цепочку: Пустой -> x -> y (Shape A)
const obj1 = {};
obj1.x = 1;
obj1.y = 2;

// Порождает цепочку: Пустой -> y -> x (Shape B)
const obj2 = {};
obj2.y = 2;
obj2.x = 1;
```
Поскольку obj1 и obj2 имеют разные скрытые классы, функции, принимающие эти объекты, деоптимизируются. 
Если постоянно добавлять новые случайные свойства, V8 сдается, уничтожает структуру Shapes и переводит объект в Dictionary Mode (режим хэш-таблицы/словаря). 
Объект превращается в медленную ассоциативную карту памяти, поиск по которой в разы медленнее.

### Проблема: Оператор delete
Когда используется delete obj.x, V8 не просто стирает значение. Скрытые классы не умеют «удалять» переходы назад. 
Этот шаг автоматически и безвозвратно переводит объект в Dictionary Mode.

### Оптимизация
```
// ПЛОХО
function User(name) {
  this.name = name;
}
const user = new User("Иван");
if (hasAccess) user.role = "admin"; // Разрушает общую форму класса для пользователей без доступа

// ХОРОШО
function User(name, role = null) {
  this.name = name;
  this.role = role; // Форма объекта всегда одинаковая!
}
const user = new User("Иван", "admin");

// Вместо delete
// user.role = null; (или undefined)
```

### Уровни оптимизации элементов (от самых быстрых к медленным):
1. PACKED_SMI_ELEMENTS: 
Массив содержит только целые числа (Small Integers) и не имеет пропусков ([1, 2, 3]). 
Выделяется непрерывная память. Бешеная скорость.
2. PACKED_DOUBLE_ELEMENTS: 
Как только вы добавили одно число с плавающей точкой ([1, 2.5, 3]), весь массив переходит на этот уровень. 
Памяти требуется больше.
3. PACKED_ELEMENTS: 
В массив попала строка или объект ([1, 2.5, "привет"]). Теперь элементами могут быть любые указатели.
4 - 6. HOLEY_* (Разреженные массивы): 
Массивы с «дырами» ([1, , 3]).
Почему дыры (Holes) — это катастрофа для производительности?
Если вы пытаетесь прочесть arr[1] в массиве [1, , 3], движок видит, что значения по индексу 1 нет. 
Но спецификация JS требует проверить: вдруг свойство 1 есть у прототипа массива (Array.prototype) или у Object.prototype?
Движок останавливает быстрый цикл и начинает лезть вверх по всей цепочке прототипов.

### Как оптимизировать:
Никогда не создавайте массивы через new Array(10). 
Если нужен пустой массив под заполнение, используйте Array.from({ length: 10 }, () => 0) или .fill(0).
Не смешивайте типы данных в критических для скорости массивах.

## TypedArrays (Типизированные массивы)
Обычный Array в JS динамически меняет размер. Для TypedArrays выделяется фиксированный буфер (например, ровно 1000 байт). Изменить его размер нельзя.
Типизированные массивы (TypedArrays) состоят из двух частей:
1. ArrayBuffer — сырой кусок памяти (буфер), фиксированный по размеру, который просто хранит байты.
2. Представление (View) — специальный класс (например, Int32Array, Uint8Array), который накладывает «сетку» на этот кусок памяти, позволяя читать и писать туда числа определенного типа.
Одно из главных отличий от обычных массивов — фиксированный размер ячейки. Если попытаться записать число больше, чем вмещает тип, произойдет либо отсечение лишних битов, либо округление.

**В чем скорость**: Движку V8 вообще не нужно думать о скрытых классах, типах данных, проверках прототипов или сборке мусора для отдельных элементов. Доступ к элементам компилируется напрямую в процессорные инструкции (как в C).
**Сценарий**: 
1. Работа с бинарными протоколами и файлами (Сеть и I/O)
Если ваше приложение общается с сервером по низкоуровневым протоколам или парсит файлы (картинки, аудио, архивы), данные приходят в виде байтов.
Пример: Загрузка файла через WebSockets, парсинг Protocol Buffers (Protobuf), чтение кастомных бинарных форматов.
Почему не Array/Map: Обычный массив превратит каждый байт файла в полноценное 64-битное JS-число (8 байт на число + накладные расходы на сам элемент массива). 
Файл размером 10 МБ в обычном массиве легко раздуется до 80–100 МБ в оперативной памяти. Uint8Array займет ровно 10 МБ — байт в байт.
2. Высокоинтенсивная математика и WebGL (3D и 2D графика)
Когда вам нужно отрисовывать графику через Canvas API, WebGL или WebGPU (3D-движки вроде Three.js, Babylon.js), видеокарта требует данные в строго определенном бинарном формате.
Пример: Массив из 500 000 координат \(X, Y, Z\) для частиц в трехмерном пространстве.
Почему не Array: Стандартный массив будет вызывать постоянные задержки, так как при передаче данных в WebGL движку JS придется полностью перебирать весь массив, валидировать типы каждого элемента и конвертировать их в бинарный вид на лету. 
Float32Array передается в видеокарту мгновенно одной системной командой, так как данные уже лежат в нужном процессору формате.
3. Борьба с Garbage Collector на больших объемах данных
Если в вашем приложении (особенно в Node.js на бэкенде) постоянно создаются, фильтруются и уничтожаются массивы со сотнями тысяч элементов, сборщик мусора начнет тормозить всю программу (вызывая просадки FPS или задержки ответов сервера).
Пример: Обработка логов в реальном времени, гео-координаты, финансовые котировки.
Почему не Array: Удаление обычного массива из 1 000 000 элементов заставляет GC обходить миллион объектов или указателей. Если вы используете один зафиксированный Int32Array, для GC это всего один объект. 
Вы можете занулить его элементы вручную, переиспользовать буфер, и сборщику мусора вообще не придется напрягаться.
4. Критические по скорости CPU-вычисления
Если вы пишете алгоритмы шифрования (криптография), архивации (сжатие данных в браузере), обработку аудиосигналов в реальном времени (Web Audio API) или физический движок.
Пример: Хэширование строк (SHA-256), декомпрессия ZIP на клиенте, применение аудио-фильтров (эквалайзер).
Почему не Array: В TypedArrays все элементы лежат в памяти друг за другом (последовательно). Процессор компьютера считывает такие данные в свой сверхбыстрый L1/L2 кэш целиком. Обычный массив JS может быть разбросан по разным адресам памяти кучи (Heap), из-за чего процессор постоянно «промахивается» мимо кэша и ждет медленную оперативную память.
5. Обмен данными между потоками (Web Workers / SharedArrayBuffer)
В JavaScript тяжелые вычисления часто переносят в фоновые потоки (Web Workers), чтобы интерфейс не зависал.
Пример: Тяжелый расчет физики в игре перенесен в Worker.
Почему не Array: При передаче обычного массива или объекта в Web Worker движок делает полную глубокую копию (Structured Clone Algorithm). Если массив весит 50 МБ, на его копирование уйдет куча времени. С TypedArrays вы можете использовать SharedArrayBuffer — оба потока (главный и фоновый) будут смотреть на один и тот же кусок физической памяти без какого-либо копирования.

Краткая шпаргалка для выбора:
Используйте Array, Set, Map: В 95% стандартных задач. Когда важна гибкость, удобные методы (.map(), .filter()), динамический размер и работа со строками или объектами.
Используйте TypedArrays: Когда данные — это только числа, их очень много (от десятков тысяч до миллионов), критична скорость вычислений или идет прямая работа с API браузера (Canvas, WebGL, Web Audio, WebSockets).

## Map и Set против Object и Array
### Map вместо Object для динамики: 
В отличие от Object, Map изначально спроектирован так, что в него будут постоянно добавлять и удалять ключи. 
Он не использует скрытые классы (Shapes), поэтому частые мутации не приводят к деоптимизации кода движком. 
Хэш-таблица Map оптимизирована на уровне C++ внутри V8 под частую вставку и удаление.

#### Когда предпочтительнее Map (вместо Object)
Хотя Object и Map оба хранят пары «ключ-значение», движок JavaScript оптимизирует их совершенно по-разному.
**Частая вставка и удаление ключей (Динамика)**: 
Если ваша коллекция постоянно мутирует в процессе работы программы (ключи добавляются и удаляются сотни или тысячи раз), выбирайте Map. 
Он написан на C++ на уровне движка V8 и оптимизирован под частые мутации. Object при частой вставке теряет оптимизацию скрытых классов и начинает тормозить.
**Ключи произвольного типа**: 
В Object ключами могут быть только строки или символы (Symbol). 
Если вы попытаетесь сделать ключом другой объект или массив, он приведется к строке "[object Object]". 
В Map ключом может быть что угодно: другой объект, функция, число, массив или DOM-элемент.
**Важен порядок вставки**: 
Map строго гарантирует, что при итерации элементы будут возвращаться в том порядке, в котором они были добавлены. 
В Object порядок сортировки ключей сложный (целые числа сортируются по возрастанию, строки — по времени добавления), что часто приводит к багам.
**Нужен размер коллекции здесь и сейчас**: 
У Map есть встроенное свойство .size, которое возвращает количество элементов за время O(1). 
Чтобы узнать размер обычного объекта, вам придется вызвать Object.keys(obj).length, что заставит движок полностью обойти объект, тратя время O(n).

#### Когда предпочтительнее Object (вместо Map)
**Записи с фиксированной структурой (Формы/DTO)**: 
Если вы создаете объект один раз (например, данные пользователя из API: { id: 1, name: "Ivan", role: "admin" }) и потом только читаете или обновляете значения существующих полей, Object — идеальный выбор. 
Движок создаст для него скрытый класс (Shape) и доступ к свойствам будет происходить на максимальной скорости.
**JSON-сериализация**: 
Объекты нативно поддерживают JSON.stringify(obj) и JSON.parse(str). 
Чтобы передать Map по сети в формате JSON, вам придется вручную конвертировать его в массив или объект и обратно.
**Простая конфигурация**: 
Для хранения статических настроек приложения (например, констант) синтаксис объекта config.theme гораздо лаконичнее и привычнее, чем config.get('theme').

### Set.has() вместо Array.includes(): 
Метод includes() перебирает массив линейно: от 0 до N (сложность (O(n))). 
Если в массиве 50 000 элементов, поиск последнего займет 50 000 операций. 
Set — это хэш-таблица. Метод has() берет хэш от ключа и мгновенно находит его в памяти за 1 операцию (сложность (O(1))), независимо от размера коллекции.

#### Когда предпочтительнее Set (вместо Array)
**Проверка на уникальность и наличие (Поиск за O(1))**: 
Если главная задача вашего кода — отвечать на вопрос «Есть ли этот элемент в коллекции?», используйте Set. 
Метод Set.prototype.has() работает по хэш-таблице мгновенно, независимо от того, лежит там 10 элементов или 1 000 000. 
Метод Array.prototype.includes() выполняет линейный перебор всех элементов (O(n)) и на больших объемах данных парализует выполнение кода.
**Хранение только уникальных значений**: 
Set автоматически игрирует дубликаты. Если вам нужно собирать коллекцию уникальных ID, Set избавит вас от необходимости писать проверки if (!arr.includes(id)).
**Частое удаление элементов**: 
Удалить элемент из Set через .delete(value) происходит за O(1). 
Удаление элемента из середины Array через .splice() заставляет движок сдвигать в памяти все последующие элементы, что крайне неэффективно на больших массивах.

#### Когда предпочтительнее Array (вместо Set)
**Важен строгий порядок по индексам**: 
Если вам нужен доступ к элементам по их порядковому номеру (arr[0], arr[5]), массивам нет альтернатив. 
В Set получить элемент по индексу невозможно.
**Манипуляция данными (Сортировка, Фильтрация, Трансформация)**: 
Массивы обладают богатейшим встроенным API: .map(), .filter(), .reduce(), .sort(), .reverse(). 
У Set практически нет методов для трансформации данных, его придется сначала преобразовывать в массив.
**Разрешены дубликаты**: 
Если логика приложения подразумевает, что один и тот же элемент может встречаться в списке несколько раз (например, история покупок или стек вызовов), Set использовать нельзя.

### WeakMap и WeakSet (Борьба с утечками)
В JS объект живет в памяти, пока на него есть хоть одна ссылка.
```
let cache = new Map();
let user = { name: "Петр" };

cache.set(user, "какие-то данные");

// В коде пользователь нам больше не нужен
user = null; 
```
Проблема: Объект { name: "Петр" } останется в памяти навсегда, потому что он все еще лежит в качестве ключа внутри cache. 
Сборщик мусора (GC) не имеет права его удалить. Это классическая утечка памяти.

**Решение с WeakMap**:
```
let cache = new WeakMap();
let user = { name: "Петр" };

cache.set(user, "какие-то данные");
user = null; // Теперь объект полностью удален из памяти!
```
WeakMap удерживает слабую ссылку. Для сборщика мусора присутствие объекта в WeakMap не считается живой ссылкой. 
Как только user = null удаляет внешнюю ссылку, GC при следующем проходе уничтожает объект { name: "Петр" } и автоматически вычищает запись из WeakMap.
Ограничение: Ключами в WeakMap могут быть только объекты (или зарегистрированные символы), так как примитивы (например, строки или числа) не имеют жизненного цикла и не отслеживаются сборщиком мусора.
